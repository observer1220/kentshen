這兩年有幾起新聞，某些靠 AI 快速做出來的服務把客戶名單外洩了。仔細看成因，幾乎都不是密碼學選錯演算法，而是非常基本的疏忽。我替自己的登入中樞 auth-hub 做了一次對照檢查，把結果整理成下面這份表。你也可以拿去檢查自己的專案。

## 十項檢查

**1. 資料庫有沒有直接暴露給前端？**
用 Supabase 或 Firebase 這類服務時，如果公開金鑰搭配沒設好的存取規則，任何人都能直接查資料。我的做法是資料庫完全不對外，前端永遠只能打 Worker 的 API，資料存取全部寫在後端。

**2. 密碼是不是明碼存放？**
使用者端我只留 Google 登入，沒有密碼可以猜。管理後台的密碼則用 PBKDF2-SHA256、21 萬次迭代、每個使用者獨立的 salt，比對時用常數時間，避免被時間差攻擊。

**3. 金鑰有沒有寫在程式碼或 repo 裡？**
所有機密（JWT 簽章金鑰、Google Client Secret、管理密碼）只用 `wrangler secret put` 存在 Cloudflare，不出現在程式碼或 `wrangler.toml`。本機用的 `.dev.vars` 一定要放進 `.gitignore`。

**4. 後台管理 API 有沒有驗證？**
後台只認一組獨立的管理密碼（可再加 TOTP）登入後的 session cookie，不收一般使用者的 token。後台完全不開 CORS，寫入請求的 `Origin` 必須是後台自己。同一個 IP 密碼錯 5 次就鎖 15 分鐘。

**5. 有沒有 SQL Injection？**
所有查詢都用 D1 的 prepared statement 搭配 `bind()`，沒有任何字串拼接組 SQL。讓 AI 寫查詢時，這一點要特別檢查，因為模型常常會為了方便直接拼字串。

**6. CORS 是不是設成 `*`？**
CORS 用白名單，只有 `ALLOWED_ORIGINS` 裡列出的網域可以帶 cookie 呼叫 API。設成 `*` 的話，任何網站都能借用使用者的登入狀態打你的 API。

**7. Token 有沒有永久有效？**
access token 只活 15 分鐘。refresh token 存在資料庫裡的是雜湊值，不是明碼，而且每次刷新都撤銷舊的、發新的，單一 token 外洩可被利用的時間很短。

**8. 有沒有頻率限制？**
每個 IP 每分鐘最多 120 個請求，後台登入每分鐘最多 10 次，使用 Workers 的 Rate Limiting。被擋下的掃描會寫成 `security: true` 的 JSON log，之後可以在 Workers Logs 查到。

**9. Log 裡有沒有印出密碼或 token？**
程式碼裡沒有任何地方 log 密碼或 token 的明文。這點最容易在除錯時不小心犯：一行 `console.log(req)` 就可能把所有東西印出來。

**10. 資料表會不會無限成長？**
每天排程清理過期的 refresh token、OAuth state 與舊紀錄，後台也看得到用量。D1 被塞爆之後所有寫入都會失敗，這種故障很容易被忽略，直到某天使用者突然登不進去。

## 還沒做完的事

誠實地說，我也還有清單上沒打勾的項目：

- 串金流之前，Webhook 一定要驗證簽章。Stripe 看 `Stripe-Signature`，綠界看 CheckMacValue，否則任何人都能偽造「付款成功」的請求幫自己開權限。
- 如果要開放帳密登入，email 驗證、忘記密碼、Turnstile 與依 IP 的失敗計數都要先做。
- 定期檢查 `audit_log`，管理員對權限的每個異動都有紀錄，出事時才回溯得到。

## 給用 AI 寫程式的人

AI 能快速寫出可以運作的程式，但「可以運作」和「安全」是兩回事。我的習慣是把這份檢查表當成固定的收尾步驟：功能做完，逐項對照一遍，再上線。花不到一小時，換來的是不會上新聞。
